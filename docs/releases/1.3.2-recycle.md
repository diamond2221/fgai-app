# 1.3.2 NAS 工程归档统一

2026-10-11 用户要求彻底删除先归档到普通 `FgStudio/recycle`，不使用 NAS 系统 `#recycle`。

| 工程 | 归档目录 | 规则 |
| --- | --- | --- |
| 自由画布 | `recycle/canvases` | 前端回收站保留 30 天，可恢复；手动彻底删除或到期清理先写入工程与历史 JSON，成功后清理数据库正文，资源引用保留 |
| 广告 | `recycle/adcraft/<工程ID>` | 保持现有完整工程目录及数据库快照归档 |
| 小说 | `recycle/arcreel/<账户ID>` | 只挂载本账户回收目录；文件完整复制及哈希校验后移除原工程；记录收尾与失败回滚保持事务一致 |
| 综合工作台 | `recycle/opencreator/<账户ID>` | 已归档且无活动任务的托管工程可彻底删除；先完整归档独占文件和工程记录，批次失败恢复源目录 |

普通删除与“彻底删除”区别保留。进入 NAS recycle 后不再通过产品回收站恢复，也没有新增自动物理清空 NAS 归档的任务。工程归档不清理共享素材、其他账户、账单或运维备份。

代码与免费验证：自由画布后端归档、权限和保留期回归通过；前端 TypeScript 与实际 `/fg-six/` 构建通过。小说归档的原文件保留、外部目录拒绝和复制失败保护测试通过；综合工作台实际 SQLite 回收站测试及完整文件归档测试通过。镜像复用既有依赖，无新增供应商付费请求。

实机结果（2026-10-11）：

- 自由画布完整通过删除、恢复、其他管理员及成员越权拒绝、手动彻底删除、重复清除幂等和删除后隐藏检查。归档 JSON 为 217839 字节，保留 1 个历史版本及 4 条素材引用。仅将新建验收画布的回收时间改为 31 天前，实际启动清理器成功归档到 `recycle/canvases`；未修改已有用户工程的到期时间。
- 小说与综合工作台的真实 NAS 文件夹测试仍未通过最后的源目录移除。两者均已写入完整归档，但 Mac SMB 留下 `.smbdelete…`，`rmdir` 返回 `ENOTEMPTY`。代码因此不把数据库删除记为成功，并尝试恢复已删除的源文件；这些测试不等于工程彻底删除已通过。不要重复尝试清理用户工程来绕过该错误。
- 小说补丁镜像曾因从受限传输目录复制了不可供普通用户读取的启动文件而反复重启，现已修复并在镜像中以 `fg` 用户验证文件读取、Python 编译和回收模块导入。管理员与成员两个小说运行时的 `/health`、`/api/v1/projects/` 均返回 200。主站、画布前后端及网关均为 healthy；未重启 Nginx 或 Docker。
- 实机镜像：画布后端 `fg-release132-backend:unified-recycle`、画布前端 `fg-release132-web:unified-recycle`、小说 `fg-release132-arcreel:recycle-readable`、综合工作台 `fg-release132-opencreator:unified-recycle`。本轮无新增供应商付费请求。

这份记录不代表所有模型、所有 Agent 或 Skill 全流程通过。素材库底层对象删除（`resource_delete.go` 与主站 `lib/local/storage.ts`）、故事项目等其他删除入口仍须逐一核对归档规则，不能由上述四类工程推定全系统已经覆盖。HTTPS 原证书及私钥文件本轮仍未找到；运行中的证书不能代替重启所需文件。
